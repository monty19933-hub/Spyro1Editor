## Conclusion and meaning

The exact world-key handler has no direct treasure-award or gem-emitter call,
and its direct stores do not target the treasure counters. That statement is
stronger than interpreting selectorFF as zero, but is **not yet a complete
transitive non-award certificate**. A real additional dependency is the HUD's
separate AD key actor and particle path when global key state changes.

The seven deterministic source selectors still total20: Wizard10 and
chest/rewards10. The key causes chest activation; that causal relationship must
not add a second copy of the chest's already-counted10. The unresolved question
is whether ordinary key pickup/display adds **its own** treasure credit.
SelectorFF is not evidence either way: existing witness472 demonstrates an
emittedFF selector reaching native RNG.

## What remains before a source-issued key-zero claim

1. Bind these **complete** source code owners to the actual current Host/EXE
   and actual AD row/private/shared-model/callback owners. Current Host issuance
   explicitly compares only the160-byte key pickup prefix, though its whole
   retained-prefix/inverse construction preserves the rest. A new proof should
   retain the274-byte owner and new helper/window comparisons explicitly.
2. Finish bounded transitive write/return ownership, not a new physics engine.
   Sound55A78 has direct callees16AB4,171FC,176C8,1778C,17908,56C84,56DC4,5C7AC,
   6272C. A sound label or lack of direct3B854 call does not certify their
   effects. Sparkle3AAEC depends on bounded slots77108..771C7, the already-narrow
   mode4/transform/vector/RNG leaves, and valid callee-preserved registers.
3. Bind the particle callback's table entry, complete allocation/common-loop/
   return owners, and both world/HUD AD index ranges. The current script leaves
   computed transfers explicit; it does not fabricate a returned particle.
4. Close the HUD display helpers542E4/54400/5445C/544A8 and the ordinary generic
   simple-model presentation consumer's RAM-write owners. The literal AD
   initialization and a data-only PETE model do not certify generic rendering.

Known real award control remains3B854: direct stores3B8BC/3B8C0 update global
80075860 and the selected level counter based at80077420. A future proof must
exclude both calls and direct/aliased counter writes under explicit valid-owner
premises, not just search for a function name or selector.

The practical next proof can therefore be a bounded memory-effect certificate
for these actual source owners, with GTE results treated as numeric values only
where complete store destinations are independently fixed. It need not claim
the entire engine, chest lifecycle, every retail key, or actual runtime safety.
Until those remaining owners close, preserve the explicit experimental key-zero
premise. Observing no treasure change during exact-candidate key pickup/HUD
animation would add useful **runtime path evidence**, not universal source proof.
