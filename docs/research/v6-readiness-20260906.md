## The short answer

A useful V6 beta and "every Moby and texture in every level" are different
milestones. A beta can expose the tested new capabilities with accurate limits.
Universal native portability still includes unsolved engine/resource handling
and gameplay validation. There is no defensible completion percentage or date
for that promise yet; the inventory size and number of passing checks are not
percentages of universal compatibility.

| Area | Established now | What remains for the requested V6 |
| --- | --- | --- |
| Native Moby selection | Source variants across all 35 retail levels can be browsed; existing approved templates can be selected | General native import planning, complete dependencies, integration into placement/export and broader gameplay coverage |
| Cross-level retail textures | All 35 destinations enumerate the other 34 donors through the production shared replacement route | Each actual material/target must fit the native descriptor, runtime-control and storage rules; arbitrary animated/custom/private additions are not generally supported |
| Fresh level | A new native floor/scene, LAB title and player/companion ran in DuckStation without Town Square terrain; authored values drive native compilation; project-bound save/reopen now passes tests | Viewport/undo, edited-document output and action/transition tests |
| Fresh textures | Two real cross-level materials compile through the paired resource/upload/body path | Textured disc composition, source-bound output, gameplay/near-far rendering tests and editor controls |
| Release | Existing editor behavior and the last default Release gate are preserved | Assemble the new workflow, run end-to-end UI/export/game tests, package a separately identified V6 preview and then release |

## What “available in any level” must mean

The editor must carry an imported object's actual behavior and dependencies,
not just make its model visible. The engine must be able to address its models,
animations, properties, child actors/effects, audio and shared state correctly
in the destination. Native save/reward identity and finite resource capacities
also have to survive reloads and combinations with unrelated destination actors.
Selection from a complete library is necessary but not sufficient.

The current inventory covers placed rows and local registrations across the
35 retail levels; it does not claim an exhaustive catalogue of global-only or
dynamically emitted actors. The reusable machinery can allocate/relocate
supplied source-proven dependencies, but it does not yet discover and satisfy
arbitrary behavior dependencies automatically.

The existing key/chest case also has shared mutable native key/gem state; a
second family cannot be made independent just by copying private properties.
Wizard scene append/placement is count-aware, but the current Dark Hollow
overlay still binds 129 placed rows/90 dynamic slots, and reward integration
still requires one appended Wizard. A complete two-Wizard candidate therefore
needs more composition work before its gameplay test, not simply a larger
scene list. The relevant source is `NativeDarkHollowWizardOverlayPlan.cs` and
`NativeDarkHollowWizardDeathRewardPlan.cs` under Core/Exporting.

The target is broad native portability with usable compatibility/capacity
diagnostics. It is not a promise of unlimited simultaneous objects or textures.
Unsupported cases must be identified before output; an unsupported case is not
silently made compatible by enabling a button or copying a model registration.
