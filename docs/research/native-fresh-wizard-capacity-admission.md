## What the original checks actually cover

The free>=21 rule is in bolt-impact recursion at7EBA8..7EBC8. It is checked
before each child and caps the loop at four, while the parent remains live.
The three Wizard primary calls82DB4/82DF0/82E38 do not read capacity or active
count. An actual active32 fixture still reaches the unchecked524C4 allocator.
The three calls represent separate update stages, not three simultaneous shots.

The N32 body owns32 row/private pairs plus the allocator's complete next-row
reserve. This bounds storage; it does not guarantee every reachable event has
room. One ten-value pickup creates two number104/105 actors while the gem still
exists: active30 fits this bounded request, active31 does not. A primary guard
allowing the last free row would leave no headroom for that later event.
Reward/fallback creation and absent-Sparx replacement have other direct calls.
Their complete scheduling, visibility pauses and target lifetimes remain open.

The ordinary256-entry particle pool behaves differently: request257 selects
an existing owner using real RNG rather than writing beyond the pool. A
256+20 request witness produced19 distinct replacement slots for seed1, with
unchanged end cursor. This is allocator behavior, not whole particle setup or
acceptable visuals. The actual pool initializer writes a four-byteFFFFFFFF
terminator; the last-free branch delay reads its second byte. Exact terminator
ownership, last/middle free and reuse pass; a missing-byte control refuses.
The separate eight-sparkle path is not this pool or the dynamic Moby arena.

## Narrow prototype and engineering decision

A private13-word guard intercepts only the three primary callsites. It requires
capacity32 and unsigned active<32, then tail-jumps to the existing spawn26.
Otherwise it takes the donor's existing model-update/leave continuation. The
original stage store still executes, so refusal consumes that shot rather than
retrying later. That is an explicit proposed behavior change, not a native
guarantee or an approved final exhaustion policy.

Primary callers discard the returned pointer; the recursive impact caller
immediately dereferences v0+44. Therefore a global allocator change returning
null, a stale row or a sentinel is not safe. The prototype leaves that caller,
the global callback, original Town/Dark and all old Host bytes unchanged.

Admitted paths match unguarded registers except at/v0/v1, HI/LO and the complete
spawn frame through actual524C4 entry. Root separately read the pinned complete
allocator: it overwrites those three registers before their first reads. No
successful allocation/return is invented. Refused paths stop at real529E4;
a separate post-update witness restores every Town GPR/SP/HI/LO and outer frame,
then executes exactly one actual list-cursor advance. The model-update helper
and full visibility/frame are not executed by this test.

The current24C padding could fit34 bytes only after a new explicitly named
owner and revised partition; existing padding is not available scratch space.
The test-only801D0000 guard is not a proposed native RAM allocation.

Do not promote a primary-only guard as the capacity fix. A complete policy must
cover the remaining reward/digit/Sparx requests without silently losing treasure,
prove counter/cursor/sentinel consistency and preserve callers that require real
actors. Reserving an arbitrary three or twenty slots is not an aggregate proof.
This is the next capacity contract, separate from detached EXE/disc assembly.
